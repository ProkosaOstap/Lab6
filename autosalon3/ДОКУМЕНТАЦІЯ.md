## 4. Транскрипт відеопрезентації

Вітаю! Мене звати Остап Прокоса, і я представляю четверту частину лабораторної роботи «Автосалон» — RESTful API. Застосунок збережує веб-інтерфейс і панель керування з попередніх частин, а головне нововведення — модуль api.js, який відкриває повний програмний доступ до даних системи: до таблиць марок, комплектацій, клієнтів, опцій і продажів.

Почнемо з кореня API. Запит GET на адресу /api повертає опис усіх ендпоінтів — свого роду самодокументований каталог. GET /api/brands повертає JSON-список марок, GET /api/brands/1 — один запис за ідентифікатором. Всі відповіді — виключно JSON.

Авторизація в API подвійна: браузерна сесія або заголовок Authorization Basic для програмних клієнтів. Продемонструємо через curl: запит GET /api/brands без облікових даних віддає дані — читання відкрито. А спроба створити запис без входу повертає 401 — не авторизовано.

Тепер створимо запис як менеджер: curl з прапорцем -u manager:manager123, метод POST на /api/brands з JSON-тілом — нова марка додається, сервер відповідає кодом 201 Created і самим створеним обʼєктом. Оновлення — метод PUT: змінюємо назву марки, отримуємо 200 OK зі свіжою версією запису. Видалення — DELETE, код 200.

Валідація в API та сама, що у веб-формах: POST із порожньою назвою повертає код 400 з тілом "error" та словником "errors" по полях. Видалення запису, на який посилаються інші таблиці, повертає 409 — конфлікт: сервер не дозволяє ламати цілісність даних.

Права ролей теж дотримуються: відвідувач, навіть авторизований, на мутаційні запити отримує 403 — заборонено, тоді як manager і admin мають повний доступ.

Веб-інтерфейс при цьому продовжує працювати як завжди: панель керування, форми, списки — усе поверх того самого API-шару даних.

Підсумую: четверта частина перетворює автосалон на систему з повноцінним RESTful API — стандартизовані методи GET, POST, PUT і DELETE, JSON-відповіді з коректними HTTP-кодами 200, 201, 400, 401, 403, 404 і 409, автентифікація Basic для клієнтів і розділення прав за ролями. Дякую за увагу!
